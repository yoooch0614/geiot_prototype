# 個性発見アルゴリズム 実装計画（設計案準拠版）

VORNコンテスト（締め切り 2026-11-20）に向けた実装計画。
方式は `設計案_個性推定アルゴリズム.md`（遊び方の記録 → 16 指標 → 5 軸 → 得意・接し方・習い事）に従う。計算式・指標表・文面の詳細は設計案を正とし、この文書は「何を、どこまで、どの順で実装するか」を扱う。
実装の根拠と変更履歴は `アルゴリズム仕様と根拠.md`、現状の整理は `実装状況と今後の見込み.md`（2026-10-18 時点）を参照。
改訂日: 2026-11-19

## 1. 守ること（作業ルール）

1. このプロダクト内の情報（子どもの写真・絵・記録・コード）を外部に送らない。
2. 有料のサービスを使わない。
3. インストール・ダウンロードが必要になったら、必ず事前にユーザーへ確認する。
4. 実装していないものを、実装したと書かない（コンテスト資料も同様）。

## 2. 方針

- 子どもが絵のミッションで遊ぶだけで、遊び方の記録から 5 軸（O/C/Ex/A/ES）を推定し、「得意」「接し方」「習い事」の 3 つに変える。保護者の入力は使わない。
- 絵そのものより「描き方・選び方」を測る（ステルス・アセスメントの考え方）。
- 指標ごとに根拠の強さ（前例あり／近い前例あり／構想由来・未確認／仮説）を付け、重みに反映する。
- 表示は「事実 → 傾向 → 提案」の順。断定や「苦手」という言葉は使わない。診断ではなく、遊びを振り返る手がかりとして見せる。
- 端末内で完結する。VLM / LLM / バックエンドは使わない。記録は端末内（localStorage と IndexedDB）に保存し、画像そのものは記録に含めない。
- 発表では、**遊ぶ（絵を何枚か描く）ほど、個性ページの値と文が変わる様子を動画で見せる**。これを実装の中心にする。

## 3. 範囲

### 今回実装する
1. 遊びの記録（`Session.plays`）と、7 種の仕掛け（えらぶ／むずかしい版／まって／だれと・だれに／おはなしの分かれ道／もうひとつ／きもち）
2. 16 指標 → 5 軸の計算、確からしさ 3 段階
3. 出力 1（得意とこれから伸びるところ）、出力 2（接し方）、出力 3（習い事の提案、サンプルデータ）
4. 分析画面の表示（「まだ少ない」、確からしさの段階、事実の一文）
5. デモ（`?demo=1`）
6. 好きな色の表示（K-means、`drawingFeatures.js`）。5 軸の計算には使わない

### 将来の発展として置く
- 出力 4 好きなこと（描いたものの画像認識）。モデルの導入が必要で、子どもの絵での精度も未検証。
- 教室アンケートによる習い事データと、マッチ度の式。
- 協力家庭での答え合わせ（既存の尺度との相関）と、同じ子の 2 週間後の安定性の確認。
- 年齢帯ごとの基準（当面は 0.5 の固定）。
- 職業データベースによる将来性の予測、深層学習による推定（正解データがない）。

## 6. デモ（発表の動画）

- 見せたい流れ: 0 枚で「まだ少ない」 → 絵と遊びの記録が増えるほど、5 軸・得意・接し方・習い事が変わり、確からしさの段階が上がる。
- 入力の方針:
  - 普段: 紙に描いた絵をアプリのカメラで撮り、絵本に登録する。アプリ内の描画キャンバスは作らない。
  - デモのみ: 作成者の幼少期の絵を端末内のファイルから取り込む（`?demo=1`）。通常の画面には出さない。画像は端末内だけで扱う。絵 22 枚は `../childImages/` に置く（プロジェクトの外。サーバーの公開範囲に入れない）。
- デモの `play` の値は作成者が決めたもので、実際の子どもの記録ではない。発表でもそう説明する。
- 動画は画面収録（OS 標準機能）で撮る。

## 8. 検証方法

- 計算: node（導入不要）で、記録の組み合わせごとに 5 軸と確からしさを確かめる。同じ入力で同じ結果になること、記録が 0 件でも落ちないこと、1〜2 件で極端な値が出ないこと。
- 画面: `python3 serve.py` で起動し、ブラウザで目視する。
- 自動のブラウザ操作（`verify`、puppeteer-core）を使う場合は、導入前にユーザーへ確認する。
- コンテスト後の検証（設計案「検証の計画と書き方」）:
  1. 協力家庭（目安 30 組以上）で 2 週間遊んでもらい、保護者に既存の尺度（小学生 FFPC、未就学児 CBQ 短縮版）に 1 回答えてもらい、軸ごとに相関を見る。尺度の利用条件を確認する。
  2. 相関が出なかった指標は重みを下げるか外す。出た指標は根拠の強さを「検証済み」に上げる。
  3. 同じ子が 2 週間あけて遊んだときの値の変わり方を見る。

## 9. リスク

| リスク | 対応 |
|---|---|
| 指標と 5 軸の対応は、前例のあるものが C に偏り、A と ES は仮説のみ | 重みで影響を小さくし、A と ES は「見えてきた」までにとどめる。仮説と明記する |
| 記録が少ないうちに、極端な結果が出る | `N÷(N+5)` の縮めと「まだ少ない」で対応済み |
| 仕掛けがミッションごとに偏り、軸の証拠がたまらない | 何冊か遊ぶうちに 7 種がそろうよう配る。同じ仕掛けが続かないようにする |
| 習い事の形式の属性・文面が作成者の仮の値 | 「サンプルデータ」と明記。アンケート後に差し替える |
| 通しの確認が未完了 | 5-3 で確認し、結果を記録する |

## 10. コンテスト資料での書き方

- 動くもの: 絵のミッションでの遊び方（選ぶ・待つ・挑戦する・描き足す・気持ち）の記録から 5 軸を推定し、得意・接し方・習い事の提案に変える、端末内完結のルールベース。前例のある指標と仮説の指標を、色分けして見せる。
- 将来の発展: 描いたものの画像認識による「好きなこと」、教室アンケートによる習い事データとマッチ度、協力家庭での答え合わせ、年齢帯ごとの基準。
- 避ける表現: 「AI が子どもの特性を分析」「VLM/LLM が推論」（実装していない）、「人が調べた習い事データ」（現状はサンプル）、「検証済み」（未検証）。
- 説明を用意する点: 重みと文面は仮説で診断ではない／子どもの絵・写真・記録を外部に送っていない／無料・端末内で動く／デモの記録は作成者が決めた値。
- 生成 AI の利用（開発・挿絵・BGM・文章）は、チームで確認して事実を書く。
