## 2. 元の構想との違い

元の構想は、VLM（Gemini / GPT-4o）の API とバックエンド（FastAPI + DB）を前提にしていた。
今回は **端末内のみ・無料・外部送信なし** で実装するため、次のとおり置き換える。

| 元の構想 | 今回の実装 |
|---|---|
| VLM / LLM の API | 使わない |
| バックエンド（FastAPI、PostgreSQL / Firebase） | 使わない。端末内保存（既存の localStorage / IndexedDB） |
| OpenCV / scikit-learn の K-means | JavaScript で自前実装（導入不要） |
| ③ 好きなもの（VLM のゼロショット検出） | **今回は実装しない。将来の発展** |
| ④ 習い事の提案（LLM 推論） | ルールベース + 人が調べた JSON との照合（要確認、4-4 参照） |

## 3. 方針の決定事項（2026-11-07）

- 今回はビジネスコンテストのため、「AI らしさ」が伝わる範囲でよい。学習済みモデルの導入（③ 物体認識）は **実装しない**。
- ④ 習い事の提案は **モックデータ** で作る。画面と資料に「サンプルデータ」と明記する。
- 発表では、**絵を何枚か入れると、子どもの個性ページが変化する様子を動画で見せる**。これを今回の実装の中心にする。

## 4. 実装項目

### 4-1. ① 好きな色（K-means）
- 場所: `modules/shared/utils.js` に `extractPhotoPalette` を新設。既存の `extractPhotoColor`（車体の色の置き換えで使用）は変更しない。
- 画像を HSV に変換し、背景の白紙（明度が高く彩度が低い）や透明を除外してから、k=3〜5 でクラスタリング。
- 写真は中央付近の重みを高める。絵は背景除外を優先する。
- 各クラスタの代表色と占有率を返す。初期値は固定シードで再現可能にする。
- 絵と写真の両方で出現頻度の高い色相を「好きな色」とする。

### 4-2. ② 特性（画像特徴 → Big Five の傾向）
元の構想のマッピングを、画像特徴として実装できる形にする。

| 入力 | 特徴量 | 対応する傾向（仮説） |
|---|---|---|
| 絵 | キャンバス占有率 | 外向性 |
| 絵 | 線の細かさ・色数 | 誠実性・開放性 |
| 写真 | 近接か広角か（被写体の大きさ・ピントの鮮明さの近似） | 近接→誠実性・情緒安定性／広角→外向性・協調性 |
| 写真 | 鮮やかな色・造形物の選択 | 開放性 |

- 場所: `modules/Analysis/workStyles.js` と、画像特徴の計算を置く新規モジュール。
- 現在の `DOMAIN_TRAIT_WEIGHTS` と `COLOR_TRAIT_WEIGHTS` を、置き換えるのか併用するのか決める（要確認）。
- 重みは研究で確定した対応表ではなく、仮説。画面と資料に明記する。

### 4-3. 複数ミッションの統合
- 絵本 1 冊（例: 絵 3 枚 + 写真 2 枚）の記録をまとめて集計し、1 枚だけの偶然を平均化する。
- 単発の入力が総合結果に与える影響に上限を設ける。
- 古い記録（特徴量を持たないもの）も従来どおり動くようにする。

### 4-4. ④ 習い事の提案（モックデータ）
- 習い事ごとに「どんな子が向いているか」を、Big Five の傾向と好きな色の形でモック JSON にする。
- 特性・好きな色の結果と JSON を照合し、近い習い事を提示する。LLM は使わない。
- 資料と画面には「サンプルデータ」と明記する。「人が調べたデータ」と書くのは、実際に聞き込みをしてから。
- 将来、聞き込みと公式サイトの調査で JSON を差し替えられるよう、形式だけ先に決めておく。

### 4-4b. デモ（発表の動画）
- 見せたい流れ: 絵を 1 枚入れる → 個性ページが変わる → 数枚入れるほど、色・特性・習い事の提案が変化する。
- 入力の方針（決定）:
  - 普段: 紙に描いた絵をアプリのカメラで撮り、絵本に登録する。既存の写真ミッションのフローをそのまま使う。アプリ内の描画キャンバスは作らない。
  - デモのみ: 作成者の幼少期の絵を複数枚、端末内のファイルから取り込む。デモ用の入口にし、通常の画面には出さない。画像は端末内だけで扱い、外部に送らない。
  - 紙に描いた絵の写真は、紙の白・影・端の背景が写る。4-1 の背景除外は、こうした写真で確認する。
- 必要なこと:
  - 個性ページ（`modules/Analysis/index.js`）の固定文を、分析結果から作る文に置き換える。
  - 絵が増えたときの変化が目で見えること（色のパレット、5 軸の変化、提案の入れ替わり）。
- 動画は、画面収録で撮る（OS 標準機能。追加の導入は不要）。
- デモ用に、描画の特徴が違う絵のセット（例: 赤中心で大きく塗る絵／細かい線の絵）を用意すると変化が分かりやすい。

## 6. 検証方法

- 画像特徴・K-means: node（導入不要）で、サンプル画像の画素データを使って確認する。同じ入力で同じ結果になること、白紙・単色・透明が多い画像でも落ちないことを見る。
- 画面: `python3 serve.py` で起動し、ブラウザで目視する。
- 自動のブラウザ操作（`verify`、puppeteer-core）を使う場合は、導入前にユーザーへ確認する。
- 子どもの実際の絵・写真での確認は、チーム内で提供してもらえるデータが前提（要確認）。

## 7. リスク

| リスク | 対応 |
|---|---|
| 画像特徴から Big Five への対応は、根拠が弱い | 仮説と明記する。診断ではなく振り返りの手がかりとして見せる |
| 写真の近接・広角を、簡単な指標で判定できない | 指標を絞り、精度が出ない場合は写真側の特性は「色」のみにする |
| 聞き込みの JSON が間に合わない | 件数を絞って提案の流れだけ示す。または、将来の発展に置く |
| 絵の画像が実機でどう撮られるかで、背景除外が崩れる | 複数の撮影条件で確認する |

## 8. コンテスト資料での書き方

- 動くもの: 絵と写真の画像特徴（色の K-means・占有率・線の細かさなど）から傾向を出し、人が調べた習い事データと照合する、端末内完結のルールベース。
- 将来の発展: 物体認識による「好きなもの」の特定、職業データベースを使った将来性の予測、深層学習による推定。
- 避ける表現: 「AI が子どもの特性を分析」「VLM/LLM が推論」（実装していない）。
- 説明を用意する点: 重みは仮説で診断ではない／子どもの絵・写真を外部に送っていない／無料・端末内で動く。
- 生成 AI の利用（開発・挿絵・BGM・文章）は、チームで確認して事実を書く。
