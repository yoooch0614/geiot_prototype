# 特性分析の実装状況と今後の見込み

コンテスト応募に向けた整理メモ。コードの読み取り結果と、構想図（特性分析手法）との対応をまとめる。
内容は 2026-10-18 時点。見込みは目安であり、チームの人数や時間によって変わる。

## 1. コンテストの目的と審査基準

### 目的
1. 学生の想像力と技術力を発揮する機会の提供
2. AIを活用した新しいビジネスや社会課題解決アイデアの発掘
3. 学生と企業が交流し、未来の可能性を広げるネットワーキング機会の創出

### 審査基準
1. 社会課題への着眼点
2. アイデアの独自性/新規性
3. 実現可能性/発展性
4. 技術の活用度/実装レベル
5. UI/UX/デザイン

目的②が AI を主題にしているため、AI の活用をどう示すかが重要になる。

## 2. 現状の評価（審査基準ごと）

| 観点 | 現状 | 所見 |
|---|---|---|
| ① 社会課題への着眼点 | 強い | 外遊びと体験を絵本で促し、体験から得意や好きを見つける課題設定。 |
| ② 独自性/新規性 | 強い | 絵本・撮影ミッション・絵本日記・特性の振り返りを一つのループにしている。 |
| ③ 実現可能性/発展性 | 伸ばしやすい | 構想図の段階的な展開が、そのまま発展性の説明になる。 |
| ④ 技術の活用度/実装レベル | 最大の弱点 | 分析は手書きの重みによるルールベース。構想図との差が最も大きい。 |
| ⑤ UI/UX/デザイン | 強い | PWA/Android 対応、夜テーマ、BGM、アニメーション、多言語まで作り込まれている。 |

## 3. 構想図との対応（実装状況）

| 構想図の段 | 状況 | 実際にあるもの |
|---|---|---|
| 活動データ（撮影写真・行動記録・選択肢） | 実装済み | ミッション撮影、達成記録、絵本日記。端末内に保存。 |
| 画像分類（CNN/VLM） | 未実装 | 写真の内容は認識していない。撮影すれば達成になる。 |
| 画像解析（K-means で色や形） | 一部のみ | 彩度の高い画素の重み付き平均で代表色を1色だけ取る。K-means ではなく、形の特徴も使っていない。 |
| 行動解析（古典テスト理論） | 未実装 | 達成件数やタグを数えるだけ。 |
| 特徴量の統合（マルチモーダル融合） | 簡易版 | タグと色の重みを足し合わせる。学習による融合ではない。 |
| Big Five 推定（深層ニューラルネットワーク） | 未実装 | 手書きの重み表（仮説）で5軸に換算する。 |
| 職業データベース | 実装済み | 891職業の5因子参照値を Excel から JSON に変換して使用。 |
| 適性マッチング（コサイン類似度） | 近い形で実装済み | 差の絶対値の平均で近さを出し、上位3件を表示。コサイン類似度ではない。 |

AI と呼べる要素は、現時点ではない。

### 実装の詳細（Big Five の換算）
- 実装場所: `modules/Analysis/workStyles.js`
- ミッションの `developmentDomains`（10種類のタグ）と、写真から取った色（8色相）に、固定の重みを掛けて5軸（O/C/Ex/A/ES）へ足し込む。
  - 例: 「協力」は協調性 +1、外向性 +0.25。赤は外向性 +0.7。
- 重み表はコード中で「研究用の確定対応表ではなく、後からレビューして調整できる仮説モデル」とされている。
- 値は 36 + (重みの合計 ÷ 件数) × 64 で 36〜100 に収める。記録がないときは固定の初期値（O72, C78, Ex66, A84, ES70）を表示する。
- 職業候補は、5軸と各職業の参照値の差の平均が小さい順に上位3件。
- 写真の色の抽出は `modules/shared/utils.js` の `extractPhotoColor`。64×64 に縮小して彩度の高い画素を平均する。人の顔や身体の情報は使っていない。

### データの扱い
- `fetch` を使うのはアプリ内の JSON を読む箇所のみ。外部サーバーへ送る処理は見当たらない。
- 記録は端末内（localStorage と IndexedDB）に保存される。
- `tools/translate_work_style_titles.py` は開発時の補助ツールで、Google 翻訳の非公式な通信先を呼ぶ。アプリの実行時には使わない。

## 4. 今後の実装見込み（目安）

| 項目 | 見込み | 理由 |
|---|---|---|
| K-means による代表色の複数抽出 | 高い | 数十行で書ける。外部に何も送らない。 |
| コサイン類似度への変更（平均を引く標準化つき） | 高い | 計算式の置き換えだけ。 |
| 写真の内容分類（端末内で動く小さなモデル） | 中〜高 | 学習済みモデルをブラウザで動かす方法がある。モデルのファイルが大きくなる点と、子どもの描いた絵や写真での精度は、試すまで分からない。 |
| VLM による理解 | 中 | 外部 API なら実装は早いが、写真の送信と費用が発生する。端末内で動かすのは、今の web アプリでは重い可能性がある。 |
| 行動解析（古典テスト理論） | 中 | 質問票のような設計が要る。達成の有無だけではテスト理論と呼べない。 |
| 深層ニューラルネットワークによる Big Five 推定 | 低い | 学習の正解データ（子どもの写真・行動と Big Five 測定値の組）がない。構想図のままの実装は現実的でない。 |
| 「24指標 → 5因子」の根拠づけ | 要確認 | `occupation_big5_scores.xlsx` の値が O*NET からどう作られたかを、まだ確認していない。 |

現実的な線は「写真分類と K-means まで実装し、深層ニューラルネットワークは今後の構想にとどめる」。

## 5. 設計上の注意

- **コサイン類似度**: 5軸とも正の値で比べると、どの職業ともほぼ似た値になり、順位の差がつきにくい。平均を引く、または標準化してから比べる。
- **指標の次元の違い**: 構想図は O*NET を「24の指標」としているが、子どもの値は5軸。両者を直接は比べられないため、O*NET の指標から Big Five への変換が必要。図に抜けている工程。
- **子どもの Big Five**: 年齢が低いほど測定の安定性や妥当性が下がる。専用の尺度で、親や教師の評定で測るのが一般的。
- **プライバシー**: VLM を外部 API で動かすと、子どもの写真を外部へ送ることになる。端末内で動かすか、保護者の同意を前提にした設計が要る。
- **既存の注意書き**: 分析画面には「診断・評価を行うものではありません」という注記が3か所ある（`modules/Analysis/index.js:247`、`:473`、`:485`）。

## 6. コンテストでの伝え方

- 実装していないものを、実装したと書かない。構想図は「目指す姿」、実際に動くものは「現在のルールベース」と分けて示す。
- 「AI が子どもの特性を分析する」「AI による職業適性判定」という表現は、実態と合わないため避ける。
- 開発に生成 AI を使った場合や、挿絵・BGM・文章を生成 AI で作った場合は、その事実を書ける。チームで確認すること。
- 事前に説明を用意しておくこと:
  - Big Five への換算は仮説であり、診断ではない。
  - 子どもの写真を外部に送っていない。
  - 職業候補は将来の適性を決めるものではなく、体験を振り返る手がかりである。

## 7. 次に決めること
